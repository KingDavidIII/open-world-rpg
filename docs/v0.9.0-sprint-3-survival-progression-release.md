# v0.9.0 Sprint 3 — Survival Progression and Release Readiness

## Objective

Sprint 3 closes the first genuinely playable prototype loop. A fresh player can
start from the main menu, follow an in-game guide, gather a starter wood supply,
craft through the wooden-tool tier, mine stone, craft a stone pickaxe, reach an
explicit completion state, save, quit, and continue the same world.

This sprint also prepares the package metadata and documentation for the
`v0.9.0` release.

## Playable survival loop

1. Start a new world from the main menu.
2. Read or skip the three-page first-run guide.
3. Collect three wood-log drops placed near the safe spawn.
4. Craft wood planks.
5. Craft sticks.
6. Craft a wooden pickaxe.
7. Mine and collect three stone blocks.
8. Craft a stone pickaxe.
9. Reach the **Stone Age** completion screen.
10. Continue building, save and quit, or return to the main menu.

## Progression architecture

- `gameplay/progression.py` owns the ordered progression state machine.
- Progression stages are stable string identities suitable for persistence.
- Every transition is monotonic and revisioned.
- Objective text is renderer-independent and derived from authoritative
  inventory state.
- Stone recipes remain locked until the wooden-pickaxe stage is reached.
- Stone mining requires a selected pickaxe while the playable progression mode
  is active.
- Direct-play development mode retains the existing bootstrap inventory and is
  not constrained by the tutorial progression.

## First-run guidance and completion

- A three-page guide explains movement, inventory access, crafting, mining,
  saving, and the release objective.
- The guide can be advanced with Enter, Space, right arrow, or left click.
- Escape dismisses the guide without blocking play.
- Guide completion is persisted so Continue does not repeatedly interrupt the
  player.
- Completing the stone-pickaxe objective opens a dedicated completion screen
  with Continue Playing, Save & Quit, and Main Menu actions.
- The active objective remains visible in the gameplay HUD and inventory screen.

## Save compatibility and hardening

- Progression is stored additively inside the existing schema-v1 payload.
- No save-schema migration is required.
- Older schema-v1 saves infer a conservative progression stage from their
  inventory and remain readable.
- Malformed progression payloads fail atomically before live world, inventory,
  dropped-item, vitals, or progression state is replaced.
- Inventory, tools, durability, dropped resources, vitals, deaths, guide state,
  objective stage, and block edits round-trip together.

## Performance controls

- The objective state machine performs bounded scans over the fixed 27-slot
  inventory and introduces no world-generation, mesh, or GPU work.
- The inventory texture-atlas surface is cached instead of regenerated every
  overlay frame.
- Progression updates occur only after relevant pickup, crafting, new-world, or
  load events.
- Existing frame-local collision-column caching and chunk-streaming boundaries
  remain unchanged.
- The complete suite, both graphical orders, and voxel smoke tests remain the
  definitive release gates on the supported Python 3.11.8 environment.

## Release acceptance criteria

- A fresh New World starts with an empty inventory and three nearby wood logs.
- The guide and objective HUD make the wood-to-stone loop understandable without
  terminal instructions.
- Stone recipes cannot bypass the wooden-tool stage.
- Stone cannot be mined without a selected pickaxe in progression mode.
- Crafting a stone pickaxe produces the explicit completion state exactly once.
- Save/Continue preserves progression and guide completion.
- Existing v0.8.0 schema-v1 saves remain loadable.
- Package metadata and runtime output report v0.9.0.
- The definitive suite collects 1,670 tests with zero skips and requires 100%
  statement and branch coverage.
- Direct-play and hidden graphical smoke workflows remain available.
- Ruff, Ruff format, mypy, dependency checks, complete statement/branch
  coverage, both graphical test orders, CLI checks, and Git whitespace checks
  must all pass before the feature branch is merged and tagged.
